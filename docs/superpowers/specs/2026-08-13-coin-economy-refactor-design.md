## 一、背景与目标

### 1.1 现状问题（调研结论摘要）

1. **金币语义双重混乱**：`users.coin_total`（1元=10，等级积分，只进不出）与米大师虚拟支付代币（0.1元/金币，用户实付）同名不同物；虚拟支付"买金币"却到账 quota/会员，用户买的东西与到账权益错位。
2. **充值→权益→退款链路断裂**：退款状态机 bug（`refunds` 永远 pending）、虚拟支付订单无法退款、Web 轮询不刷会员、pending 订单无继续支付入口。
3. **虚拟支付链路脆断**：支付成功权益依赖无兜底的异步推送；回调查无订单也回 SUCCESS；服务器 env 门禁（`WX_VP_OFFER_ID` 缺失 → 虚拟支付 404）。
4. **会员/quota 双轨不闭环**：免费 quota 永不过期、等级不驱动任何功能、会员创建双实现（`CreateMembership` 死代码）。
5. **资金安全缺口**：金币累加非幂等、退款不回收金币（可"买卡→升等级→退款"刷分）、无渠道对账视图、无退款风控。

### 1.2 目标

建立**统一金币经济闭环**：

```
充值（三渠道）→ 金币到账（含赠送）→ 消费（测算/会员/私域服务）→ 权益到账 → 退款（原路+风控）
```

- 金币 = 唯一货币，语义单一、全链路可审计
- 全端（Web/小程序）充值、消费、退款入口齐全
- 资金安全：原路强制、赠送作废、风控四层、渠道对账

## 二、经济模型（决策汇总）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 改造形态 | **B 经济重构**：金币 = 可消费货币 |
| 2 | 消费场景 | 测算/会员 + **可扩展消费点**（付费加群/大师微信等私域服务，预留模型） |
| 3 | 充值模式 | **统一金币**：所有渠道只充金币，权益全用金币兑换 |
| 4 | 充值档位 | 档位 + 阶梯赠送（1元=10金币） |
| 5 | 消费定价 | 等值换算：测算 99 / 月卡 299 / 季卡 499 / 年卡 999 金币 |
| 6 | 退款模型 | **A1 半自动**：规则自动算 + 人工审批 + 自动原路退 |
| 6b | 风控 | 四层：硬规则 / 账号识别 / 行为标记 / 审计对账 |
| 7 | 支付渠道 | **Web = 微信 Native + 支付宝；小程序 = 全终端虚拟支付（微信合规强制）** |

### 2.1 货币规则

- **汇率**：1 元 = 10 金币（所有渠道统一）
- **金币用途**：兑换测算次数、会员卡、私域服务等（消费点可扩展）
- **成长值**：`coin_total` 语义改为"成长值"（累计实付金额），只影响等级展示，**与可消费余额分离**；退款按订单扣回，防刷等级
- **赠送金币**：平台营销成本，**只能消费、不可退现金**；退款时作废

### 2.2 充值档位（默认值，后台可调）

| 档位 | 实付 | 到账金币 | 赠送金币 | 折合折扣 |
|---|---|---|---|---|
| 小 | ¥10 | 100 | 10 | 9.1 折 |
| 中 | ¥30 | 300 | 40 | 8.8 折 |
| 大 | ¥50 | 500 | 80 | 8.6 折 |

### 2.3 消费定价（与现价等值）

| 消费点 | 类型 | 金币 | 权益 |
|---|---|---|---|
| 单次测算 | quota | 99 | 1 次测算（长期有效） |
| 月卡 | membership | 299 | 30 天不限次会员 |
| 季卡 | membership | 499 | 90 天不限次会员 |
| 年卡 | membership | 999 | 365 天不限次会员 |
| （预留）私域服务 | service | 本期不实现，仅建表 | 加群/大师微信等，后台交付 |

## 三、数据模型

### 3.1 users（改造）

| 字段 | 说明 |
|---|---|
| `coin_balance`（新增） | 可消费金币余额，默认 0 |
| `coin_total`（语义改名） | 成长值（累计实付），等级积分，只读展示 |

### 3.2 coin_transactions（新增，金币总账本）

```
id, user_id, order_id(可空), type, amount(有符号整数),
balance_after, channel(wxpay/alipay/virtual/system), note, created_at
```

`type` 枚举：
- `recharge` 充值到账（+）
- `gift` 充值赠送（+，关联同一 order_id）
- `consume` 消费扣减（-）
- `refund` 退款扣回（-，剩余实付金币）
- `writeoff` 退款作废（-，赠送金币清零）
- `adjust` 人工调整（±，后台操作，必填 note）

**不变量**：`sum(amount) = coin_balance`；任何变动必须落流水（原子事务）。

### 3.3 coin_packs（新增，充值档位）

```
id, coins(到账), bonus(赠送), price_fen, active, sort
```

### 3.4 products（改造为消费商品）

```
id, type(quota/membership/service), name, coins(金币价),
quota(次数), duration_days, active
```

`service` 类型新增 `deliver` 语义：消费后生成待交付记录。

### 3.5 service_deliveries（新增，私域服务交付）

```
id, user_id, product_id, status(pending/delivered), note, created_at
```

预留：付费加群/大师微信等线下交付类消费点，后台标记交付状态。

### 3.6 orders（仅保留充值订单）

- 语义：orders = **外部支付流水**（微信/支付宝/虚拟支付），一律是金币充值订单
- 新增 `order_type='recharge'` 标记（默认即可）；`channel` 已有（wxpay/alipay/virtual）
- 消费（金币换权益）不产生 orders，只记 coin_transactions + 权益表

### 3.7 refunds（修复状态机）

- 状态流转修复：`pending → approved → refunded / rejected`（当前 bug：审批不调 `ApproveRefund`，记录永远 pending）
- 新增风控字段：`risk_flags`（命中的风控规则）、`auto_amount`（系统自动计算的退款金额，审批展示）

### 3.8 其他修复

- `users.invite_code` 幽灵列：停用（不删，避免迁移风险）
- `quotas` 新增 `expires_at`：free 类型注册起 90 天有效（EEFO 优先扣即将过期）
- 删除 `CreateMembership` 死代码，会员创建统一走消费逻辑

## 四、API 设计

### 4.1 充值

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/coin/packs` | 充值档位列表（含赠送，全端共用） |
| POST | `/api/orders/coin-create` | 创建充值订单 `{pack_id, channel}`；channel 由端决定（web: wxpay/alipay；miniapp: virtual） |
| 回调 | `/api/orders/notify`（微信）、`/api/orders/alipay-notify`、`/api/orders/virtual-notify` | **改造**：支付成功 → `GrantCoinBenefits`（余额 += coins+bonus、成长值 += price_fen/10、记 recharge+gift 流水、幂等） |

### 4.2 消费

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/coin/balance` | 余额 + 最近流水 |
| POST | `/api/coin/consume` | `{product_id}` → 原子扣金币 → 按 `product.type` 发权益（quota→测算次数 / membership→会员卡（顺延逻辑复用）/ service→服务订单）→ 记流水；不足余额返回 402 |
| POST | `/api/divine/stream` | 起卦前自动扣 99 金币（消费与起卦同事务） |

### 4.3 退款

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/orders/{id}/refund` | 申请退款：系统按规则**自动计算金额**（见 §5），风控预检 |
| POST | `/api/admin/refunds/{id}/approve` | 审批通过：扣金币余额 + 赠送作废 → **按订单渠道自动原路退现金** → 状态 refunded |
| POST | `/api/admin/refunds/{id}/reject` | 驳回 |

### 4.4 后台管理

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/coin/transactions` | 金币流水查询（按用户/类型/渠道） |
| GET | `/api/admin/coin/channel-summary` | 渠道收支汇总（微信/支付宝/虚拟：收入、退款、净额） |
| GET | `/api/admin/refunds` | 退款列表（含风控标记、排序） |
| POST | `/api/admin/coin/adjust` | 人工调整金币（记流水，必填原因） |
| GET/POST | `/api/admin/services` | 私域服务交付管理 |

## 五、退款规则与风控

### 5.1 退款规则（A1 半自动）

**实付优先消耗法**：
- 每次消费先扣实付金币，赠送金币最后消耗
- 退款现金 = 剩余实付金币 ÷ 10（上限 = 实付金额）
- 赠送金币一律作废（`writeoff` 流水），不可折算现金
- 24h 窗口保留；用尽不可退

示例（充 300 送 40 = 到账 340）：
| 场景 | 剩余实付 | 退款现金 | 赠送 |
|---|---|---|---|
| 未消费 | 300 | ¥30 | 40 作废 |
| 消费 99 | 201 | ¥20.1 | 40 作废 |
| 消费 300 | 0 | ¥0 不可退 | 40 作废 |

### 5.2 风控四层

**L1 硬规则（自动）**
- 原路强制：退款渠道 = `order.channel`，无 fallback
- 退款上限 = 实付金额；赠送作废
- 24h 窗口；重复申请拒绝（唯一索引）
- 频率上限：同账号 30 天 ≤ 3 笔 且 ≤ ¥200（后台可配），超限转人工

**L2 账号识别（辅助）**
- 同手机号/设备关联多账号视图
- 注册 < 7 天退款强制人工
- 恶意退款黑名单

**L3 行为标记（不自动拦截）**
- 退款率 > 30%（退款/充值）→ 标记高危
- 充值后 < 2h 退款 → 标记疑似套现
- 单笔 ≥ ¥500 且 24h 内退款 → 强制人工

**L4 审计对账**
- `coin_transactions` 全流水（充值/赠送/消费/退款/作废）
- 渠道收支汇总视图
- 风控命中日志（谁、何时、为何转人工）

## 七、错误处理与补偿

| 场景 | 处理 |
|---|---|
| 支付回调幂等 | `GrantCoinBenefits` 按 `order_id` 判重（补金币累加幂等） |
| 回调查无订单 | 返回失败让渠道重推 + 后台告警（不再盲目回 SUCCESS） |
| 消费原子性 | 余额扣减 + 权益发放 + 流水 = 单事务；余额不足返回 402 |
| 退款并发 | 唯一索引防重复；状态机守卫 |
| 虚拟推送丢失 | 前端轮询兜底 + 后台"支付异常订单"人工对账入口 |
